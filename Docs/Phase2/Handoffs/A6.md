## Design

Rules stay in the core. Both windows only format what `SchoolWeek`/`AptitudeProjection` returned.

**Pauses cost nothing.** Constructing, reading (`ReadPreview`), editing a draft (weekday chips, attend toggle, mode chips, Edit), scrolling and closing never call a command. `school.week.order` (Save, Remove) moves no clock. Only the one "Resolve this week" button calls `Resolve()`, once per press, and only when the saved plan built successfully and has entries. Test `ThePlannerCostsNothingUntilResolve` asserts `OrderCalls == 0`, `ResolveCalls == 0` and the fake clock unmoved through all drafting.

**Firsts interrupt compression, visibly.** The preview marks every entry with `FirstOfKind || NeedsChoice` as "You play this one" and puts "Compression stops here" on the first one, with its reason: first time at this lesson, the order says play it yourself, routine not ready, scene day, or a choice only you can make (the "already used" wording when `InterruptsUsed >= 1`). These are the plan's own flags set by `BuildSchoolWeekPlan`; the UI invents none. The reason text mirrors the core's cases using only public data (`SchoolSessionsState::Periods` completed records, the lesson mode); it does not call the internal secure-family check.

**Known displaced commitments.** Per activity/lesson entry the model calls the public `DecideDisplaced` with the entry's own `Alternatives` plus the bridge's `Preview.Known` (receipt candidates for promises and appointments the player already knows). So only alternatives that were known (`KnownAt <=` decision), available and overlapping are shown, with overlap minutes. A plan the core refuses (for example `week.overlap`) shows localized words and no days; the core's English `Detail` is never displayed.

**Nominated scene days** are shown read-only with dates. The frozen contracts expose no command to nominate one (only `school.week.order` and `school.week.resolve`), so the planner does not invent one; whatever writes `SchoolWeekState::SceneDays` (A4 scenes or the integrator) is the owner.

**Recap of real receipts, never fabricated.** `BuildRecap(Plan, Result)` reads only the `SchoolWeekResult` that actually ran: `Segments[*].Outcomes` and `Disclosures`, the raw `ActivityEvents` and the real `DayLoop.Receipts.Entries` entry that each completed event points at through `ReceiptSeq` (reserved minutes, passed-over alternatives; `ReceiptSeq == 0` is reported as "recorded in the day's totals"). Facts established with a portable probe against the real core (`D:\PWWork\scratch\a6probe`): activity outcomes carry plan `(Day, Entry)` coordinates, while School/Spend/Sleep segments are single-entry `CompressWeek` runs whose `Day/Entry` are NOT plan coordinates, so those rows are described by instants only; waits are summed into one "time passed" line instead of rows; a completed event's `At` equals its outcome's `EndedAt`. A refused result gives no recap. The recap is session state (`LastRecap`, `StoreResolution`, `ClearRecap`, `RecapRevision`): after a reload there is none and the panel says so, never reconstructing one from attendance or the plan. A stop at the first entry shows "Nothing was resolved and no game time passed."

**Projection: unobserved is unknown, never weak.** `InsufficientObservation` reads "Unknown so far" in the quiet text colour; an unobserved facet reads "Unknown" (never a warning colour); the window states that unknown never means unsuitable and lists "Not yet seen (unknown, not weak)" with an invitation to try. No score: the only figure is a count of recorded observations bearing on the path's five facets. Bands/coverage/facet states are the core's. An inconsistent ledger is shown as unavailable, not as ten invented unknowns. The core's own `AptitudePrintoutLine` (English words, no digits) is shown as the detail line.

**Layout/input.** Both use the quest window's shell (corner brackets, `PWQuest::Compact/TwoPane/PanelWidth/PanelMaxHeight/ListWidth`). Planner: one scrolling column, so 853x480 to 1920x1080 and enlarged text just scroll inside the card; Back/Resolve buttons sit outside the scroll. Esc, B, menu button and LB go back (first press only); PageUp/PageDown and right stick scroll; Tab/d-pad use Slate focus navigation. Projection: list + detail (stacked when narrow), Up/Down/d-pad/left stick choose, focus on a row chooses it. No animation, so reduced motion holds by construction.

### 2. Phone entry and open handlers

The planner and terminal use the quest window's open pattern (`PWQuest::SetToggleHandler`, `PWQuestText.h:114`). In the HUD (`PerfectWorldFrontEndHUD.cpp`, near where `PWQuest::SetToggleHandler` is installed) install handlers that pause and set a "straight to this panel" flag, like `PWQuest::SetOpenOnNextPause`:

```cpp
PWSchoolProjection::SetOpenHandler([this]() { /* pause, then open the pause menu on the terminal */ });
```
The phone/menu entry only calls `PWSchoolPlanner::RequestOpen()`. It returns false when no handler is installed.

### 3. Planner callbacks: the real bridge (`IPWSchoolPlannerWorld`)

Write `MakeLaneLifePlannerWorld(...)` the way `MakeLaneLifeGate` is written (`PerfectWorldSchoolGate.h`, `IScGateWorld`): over `UPWLaneLifeSubsystem`'s one authoritative `WorldSim`. Contract of the three calls:

- `ReadPreview`: pure. Copy the live world, build the base `WeekPlan` from the commitments already known (day plan, accepted agreements), fill `Preview.Known` with `ReceiptCandidate`s for promises/appointments (`KnownAt` = when learned, `Available` per the same rule the journal uses), call `BuildSchoolWeekPlan(world, standing, sessions, base, bindings, cats)` (bindings from A1's catalogue, `cats` the bound `SchoolSessionCatalogues`), copy `standing`, `sessions`, the `ActivityCatalogue` and `Now` into the preview.
- `SetOrder(order, bRemove)`: submit `SchoolWeekOrder{order, bRemove}` (`"school.week.order"`) as the player; map `Rejection.Code` to `FPWPlannerOutcome::Code` unchanged (codes such as `school.week.overlapping_orders`; the planner maps codes to words, unknown codes read neutrally).
- `Resolve()`: build the same plan as `ReadPreview`, submit `SchoolWeekResolve{plan.Week}` (`"school.week.resolve"`). The reducer wrapper (Sonnet-owned) must apply `CompressSchoolWeek` and commit `Result.World`, `Result.Sessions`, and R9 credits from `Result.ActivityEvents` in one transaction (P2C notes, "Commands and transaction routing"). **The bridge also needs the `SchoolWeekResult` itself** for the recap; the frozen command returns only accepted/rejected, so the wrapper must publish it (for example a `LastSchoolWeekResult` kept beside the reducer, or an out-parameter on the Submit overload) and `Resolve()` must return `{Outcome, Plan, Result}`. Do not rebuild a result afterwards.
- Hold the world quiescent guard (`IsWorldQuiescent`, awake/idle/no conversation/no commerce) at the reducer, per P2C notes. Opening the planner is allowed anywhere the pause menu is; Resolve will be refused by the core with `week.world_busy` / `school.week.busy`, shown in words.

### 4. Receipt provider

`PWSchoolPlanner::StoreResolution(Plan, Result)` is the receipt provider's entry point. The planner calls it itself after its own Resolve. If anything else resolves a school week (a phone shortcut, an acceptance step), call it with the same actual plan and result. Call `PWSchoolPlanner::ClearRecap()` on load, new life and return to title so a recap never survives into another session. It is deliberately not saved, not hashed and not reconstructible.

### 5. Projection-terminal interaction

`IPWSchoolProjectionWorld::ReadLedger` returns R9's `Awakening.ProjectionEvidence` (`AptitudeLedger`, the owner P2C notes name); until R9 is in this base, return an empty ledger (every path reads unknown, which is true). The school terminal prop's `Interact(APawn*)` (campus owner: Sonnet) calls `PWSchoolProjection::RequestOpen()`. Interaction verb text: reuse `phase2.a6.projection.title`.

## Unresolved assumptions and risks

1. **Nothing in Unreal was compiled.** First compile may surface include or overload slips. I checked the `MakeText` overloads (the role overload takes no `bBold`; fixed) and every Slate construct against the quest panel. Highest residual risk: SNew expression typing in `SPWSchoolPlanner.cpp` `BuildEditor` and the `FText::Format` overloads.
2. **Rebuild inside a click handler.** Save/Remove/Resolve rebuild the body from inside the pressed button's `OnClicked`. Slate keeps the widget path alive during event routing, so this should be safe, but it is unproven in a live window; the fallback is to defer the rebuild to `Tick` (as `SPWQuestPanel::RefreshLayout` does).
3. **`SchoolWeekResult` publication** (snippet 3) needs a decision by the reducer-wrapper owner; the planner cannot make a recap without it.
4. **`Preview.Known`** (the promises list) is the bridge's job; a source of `KnownAt` for journal agreements does not exist yet. With it empty the planner honestly shows no displaced alternatives except those a base entry already carried.
5. **Lesson titles** depend on A1's text keys; until a provider is installed the capitalised subject token is used.
6. **Scene-day nomination has no frozen command**, so the planner can only display it.
7. **R9 projection ledger** is absent from this base (`Awakening.h` carries only a computed `AptitudeProjection`, not the ledger). The terminal takes the ledger through its bridge.
8. **JSON fragment:** the middle dot in `phase2.a6.clock_fmt` is a raw UTF-8 character; the core's `ParseJson` accepts it (strict JSON), but if a text loader normalises, use `\u00B7`.
9. The planner's reason text for "routine not ready" assumes any non-first, non-foreground FirstOfKind lesson under a Routine order is unmastered (the only remaining core cause); a base entry the player flagged `FirstOfKind` themselves would read the same.
10. Not done: human/cultural review of wording; 150% text, controller feel, focus order in a real window and translation length are unverified.
